## 3. 권장 실행순서

```text
문서화
  ↓
P0 사실·화면 정상화 (#1, #2, #3)
  ↓
공개 정보구조 확정 (#4)
  ↓
게시 워크플로·권한·감사 설계 (#5, #6)
  ↓
보안·개인정보 설계 (#8)
  ↓
공개 홈페이지 구현
  ↓
접근성·SEO·CI 검증 (#7, #9, #10)
  ↓
공개 MVP 운영 승인
  ↓
입주민 포털 타당성 검토 (#11)
```

- #1은 독립적으로 시작할 수 있습니다.
- #2와 #3은 관리주체 또는 권한 있는 공식 검토자가 필요합니다.
- #4 이후 개발은 공개·인증 정보분류를 먼저 확정해야 합니다.
- #5와 #6은 백엔드 구현 전에 운영절차와 데이터모델을 함께 정해야 합니다.
- #11은 #6과 #8이 끝나기 전에 구현하지 않습니다.

### Phase 6 — 입주민 포털 검토

[#11](https://github.com/skerishKang/161-bmrh-homepage/issues/11)에 따라 기능별로 결정합니다.

- `Build`: 자체구현
- `Integrate`: 외부서비스 연동
- `Link`: 공식 외부페이지 연결
- `Defer`: 운영여건 확보까지 보류
- `Reject`: 위험·비용 대비 필요성이 낮아 제외

전자투표는 기본적으로 `Integrate` 또는 `Link` 후보입니다. 별도 법률·보안·감사 검토 없이 자체구현하지 않습니다.

## 5. 릴리스 게이트

### Gate A — 프로토타입 공개

- P0 화면오류 수정
- 임시정보와 오인요소 표시
- 개인정보 없음
- 공식 사이트로 오인되지 않는 상태표시

### Gate B — 공개 MVP 후보

- P0·P1 완료
- 검증된 콘텐츠
- 관리자 게시절차
- 역할분리와 감사로그
- 보안·개인정보 기준
- 접근성 검증
- CI와 프리뷰

### Gate C — 운영 출시

- 운영주체 승인
- 관리자 MFA
- 백업·복구·롤백 검증
- 개인정보처리방침과 실제 기능 일치
- 운영매뉴얼
- 장애대응 담당자
- 운영 도메인과 보안헤더 검증

### Gate D — 입주민 기능 출시

- 주민인증 검증
- 데이터 최소수집
- 기능별 보관기간
- 개인정보 요청처리
- 권한·감사로그
- 외부서비스 계약과 책임범위
- 기능별 운영담당자

## 6. PR 분할 원칙

서로 다른 위험영역을 한 PR에 섞지 않습니다.

권장 단위:

- CSS 오류 수정
- 공식정보 정정
- 이미지 교체
- 페이지 라우팅
- 공지 데이터모델
- 관리자 워크플로
- 권한·감사로그
- 접근성
- 보안헤더
- CI

콘텐츠 승인과 기술변경이 함께 필요하면 승인증거를 PR에 연결하되 개인 연락처와 내부문서를 공개 저장소에 올리지 않습니다.
