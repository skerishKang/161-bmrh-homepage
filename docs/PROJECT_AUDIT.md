- 목적: 현재 코드를 실제 아파트 공식 홈페이지와 주민서비스로 발전시키기 전에 상태, 위험, 우선순위와 출시 조건을 문서화한다.

## 1. 요약

현재 프로젝트는 방림명지로드힐을 위한 정적 홍보·포털 UI 시안이다. 화면에는 단지소개, 공지, 커뮤니티, 생활편의, 전자투표, 시설예약, 방문차량, 민원접수와 로그인 요소가 배치되어 있지만, 대부분 실제 기능과 연결되지 않았다.

디자인 베이스는 재사용할 수 있으나 다음 이유로 운영 사이트로 사용할 수 없다.

- CSS Grid 속성 오타로 핵심 레이아웃이 브라우저에서 무시될 수 있음
- 단지 기본정보와 연락처가 공식 검증되지 않음
- 실제 단지 사진 대신 일반 외부 이미지 사용
- 비공식 브랜드와 근거가 확인되지 않은 홍보 문구 사용
- 공지·커뮤니티·생활편의·단지소개가 동일한 준비중 화면으로 연결됨
- 로그인, 관리자, 데이터베이스, 역할권한, 감사로그 부재
- 개인정보, 보안, 접근성, 자동 테스트와 출시 승인 절차 부재

따라서 현재 코드는 ‘완성된 홈페이지’가 아니라 ‘제품 방향을 논의하기 위한 정적 UI 프로토타입’으로 명확히 표시해야 한다.

## 2. 확인한 현재 구조

### 실제 정적 화면

```text
index.html
css/style.css
js/script.js
netlify.toml
```

### 동작

- `index.html`: 홈 화면, 단지정보, 갤러리, 서비스 진입 카드, 푸터
- `css/style.css`: 네이비·골드 디자인 시스템, 애니메이션, 반응형 규칙
- `js/script.js`: 한국어·영어 전환, 홈/준비중 탭 전환, 모바일 메뉴
- `netlify.toml`: 저장소 루트를 그대로 게시하는 정적 배포 설정

### 기술상태

초기 React/Vite 구조에서 Vanilla HTML/CSS/JavaScript로 방향을 변경한 흔적이 남아 있다. 현재 실제 배포 구조와 패키지·README 설명이 일치하지 않았으며, README는 이번 문서화 작업에서 실제 상태에 맞게 교체했다.

## 3. 장점

### 3.1 시각적 방향성이 있음

- 네이비와 골드를 중심으로 한 일관된 컬러 변수
- 히어로, 정보카드, 서비스카드, 갤러리, 푸터로 이어지는 명확한 화면 구성
- 데스크톱과 모바일 내비게이션을 모두 고려한 흔적
- 한국어·영어 텍스트 사전을 분리한 구조

### 3.2 공공·운영 포털로 확장 가능한 메뉴 개념

- 공지
- 단지소개
- 생활편의
- 전자투표
- 시설예약
- 방문차량
- 민원접수

다만 이 메뉴들은 현재 기능이 아니라 향후 범위 후보일 뿐이다.

### 3.3 정적 MVP로 단순화할 수 있음

첫 단계에서 읽기 중심 공개 홈페이지만 구축한다면 복잡한 애플리케이션 프레임워크 없이도 빠르게 정상화할 수 있다. 주민 개인정보를 처리하는 기능은 별도 단계로 분리할 수 있다.

## 5. 세부 분석

### 5.1 콘텐츠 신뢰성

아파트 공식 사이트에서 디자인보다 먼저 확보해야 하는 것은 사실의 정확성이다. 주소, 세대수, 동 수, 사용승인일, 난방방식, 시공사, 관리사무소 연락처와 운영시간은 하나의 검증된 데이터 원본에서 관리해야 한다.

현재처럼 동일한 정보가 HTML과 번역 JavaScript에 중복되면 한쪽만 수정되어 한국어·영어 내용이 불일치할 수 있다.

권장사항:

- 공식정보 원본을 JSON, CMS 또는 데이터베이스 한곳에 저장
- 항목별 출처와 검증일 기록
- 관리자 또는 권한 있는 대표의 승인 기록
- 임시값은 명시적으로 `미확정` 처리

### 5.2 디자인과 실제 단지의 일치

현재 UI는 고급 분양 홍보 사이트의 문법을 사용한다. 공식 관리 홈페이지로 발전시킬 때는 ‘프리미엄’보다 정확성, 공지 전달, 기록 보존과 주민 편의를 우선해야 한다.

실제 존재하지 않는 커뮤니티 시설, 스마트 시스템, 산책로 또는 브랜드를 암시해서는 안 된다. 사진은 실제 촬영물인지, 게시권한이 있는지, 차량번호·얼굴·세대정보가 노출되지 않는지 확인해야 한다.

### 5.3 공개 영역과 인증 영역

두 영역은 분리해야 한다.

#### 공개 가능 후보

- 단지소개
- 공식 공지
- 관리·점검 일정
- 공개 승인된 회의결과와 문서
- 관리사무소 안내
- FAQ
- 개인정보처리방침

#### 인증 필요 후보

- 주민전용 공지와 문서
- 본인 민원과 처리상태
- 방문차량
- 시설예약
- 주민 의견수렴
- 외부 전자투표 연결

#### 직원·위원회 전용 후보

- 작성중 공지
- 승인 대기 문서
- 감사로그
- 권한관리
- 개인정보 포함 자료
- 게시물 이전 버전

### 5.4 게시와 기록 거버넌스

공식 게시물은 최소한 다음 상태를 가져야 한다.

```text
초안 -> 검토중 -> 승인 -> 예약/게시 -> 보관
```

반려, 철회, 정정 상태도 필요하다. 게시 후 내용이 바뀌면 이전 버전, 변경자, 변경시각, 변경이유와 승인자를 보존해야 한다. 삭제는 일반 기능이 아니라 정책에 따른 보관·비공개 전환으로 설계하는 것이 안전하다.

### 5.5 접근성

현재 마우스 클릭 중심 구현을 다음과 같이 교체해야 한다.

- 페이지 이동은 `<a>`
- 실행은 `<button>`
- 현재 페이지는 `aria-current`
- 모바일 메뉴는 `aria-expanded`, `aria-controls`
- 열기·닫기 때 포커스 이동과 복귀
- Escape 키 닫기
- 명확한 `:focus-visible`
- `prefers-reduced-motion` 지원
- 200% 확대와 긴 한국어·영어 문구 검증

### 5.6 보안과 개인정보

정적 공개 홈페이지 자체는 위험이 낮지만 로그인, 민원, 방문차량, 예약, 파일업로드가 추가되는 순간 개인정보 시스템이 된다. 기능 개발 전에 다음을 문서화해야 한다.

- 어떤 데이터를 왜 수집하는가
- 누가 열람하는가
- 어디에 저장하는가
- 언제 삭제하는가
- 외부 업체에 전달하는가
- 사고가 발생하면 누가 대응하는가

전자투표는 일반 CRUD 기능과 다르다. 본인확인, 비밀성, 무결성, 중복방지, 감사, 이의제기와 법적 적합성이 필요하므로 자체 구현보다 검증된 외부서비스 연결을 우선 검토한다.

## 6. 권장 제품단계

### 단계 0 — 문서화와 사실검증

- 이슈·로드맵·범위 고정
- 단지정보 출처 확인
- 이미지와 문구 승인
- 공식/비공식 사이트 상태 결정

### 단계 1 — 프로토타입 정상화

- CSS 오류 수정
- 모바일·접근성 기본 수정
- 허위·임시 콘텐츠 제거
- 작동하지 않는 기능의 명확한 상태표시

### 단계 2 — 공개 홈페이지 MVP

- 실제 페이지 라우팅
- 공지·일정·문서·관리사무소·FAQ
- 관리자 게시와 승인절차
- 검색·공유·접근성·보안헤더
- CI와 프리뷰 검증

### 단계 3 — 운영 거버넌스

- 역할권한
- 감사로그
- 버전기록
- 백업·복구·롤백
- 개인정보정책

### 단계 4 — 입주민 포털

- 주민인증
- 주민전용 문서
- 민원
- 예약
- 차량
- 외부 전자투표 연동

## 7. 출시 금지조건

다음 중 하나라도 남아 있으면 공식 운영 출시를 승인하지 않는다.

- 공식정보 미검증
- 임시 연락처 또는 가짜 사진 사용

- 개인정보 수집 목적과 보관기간 미정
- 관리자 다중인증 부재
- 게시 승인과 감사로그 부재
- 접근성 핵심 결함
- 백업·복구·롤백 미검증
- CI 필수검사 실패
- 운영 책임자 승인 부재

## 8. 결론

현재 프로젝트는 폐기 대상이 아니다. 비주얼 구조와 메뉴 개념은 공개 홈페이지의 출발점으로 사용할 수 있다. 다만 개발 순서는 기능 추가가 아니라 다음과 같아야 한다.

1. 사실과 공개권한 검증
2. P0 레이아웃·콘텐츠 정상화
3. 공개 홈페이지 구조 확정
4. 게시·승인·감사 거버넌스 구축
5. 보안·개인정보·접근성 검증
6. 주민서비스 단계적 추가
